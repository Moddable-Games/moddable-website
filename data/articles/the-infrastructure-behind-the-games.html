Everything we ship runs on shared engines. Moddable Chess, Moddable Hexmaps, and the upcoming Moddable Rules system are open-source foundations designed once, reused everywhere. Every game, mod, and tool in our catalogue is a consumer of these engines. Here is how they fit together and why we built them this way.

Engines first, games second.

The conventional path is to build a game, then extract reusable parts later. We went the other way. Before writing a single line of Dungeon Chess, we asked: what would a chess engine need to support 70 variants, custom pieces, terrain, and AI difficulty tiers? Before drawing a hex for Nukes, we asked: what would a hex framework need to host any tile-based game from Catan to Twilight Imperium?

The answers became Moddable Chess Engine and Moddable Hexmaps. Two standalone projects, MIT-licensed, zero dependencies, zero build step. They ship independently, version independently, and work for anyone who wants to build on them. Our games are just the most demanding consumers.

Moddable Chess Engine.

MCE is a modular chess engine with 70 playable variants across boards from 4x8 to 12x8. Its architecture is plugin-based: each variant is a self-contained file that registers custom pieces, rules, win conditions, and board layouts through a declarative API.

The consumer APIs expose everything a game builder needs:

  • createGameController for full interaction loops with turn cycling, AI scheduling, and undo
  • createReplay for step-through move playback with annotations
  • renderBoard hooks including tilePainter, pieceProvider, legalMoveRenderer, and afterRender
  • buildUnitHandler for declarative piece registration (movement, attacks, abilities in config)
  • Terrain predicates for global movement constraints without per-piece conditionals
  • Effect lifecycle for timed square effects with automatic expiry

Dungeon Chess is the most extreme consumer. Four factions, 24 units, terrain hazards, special abilities, and AI opponents. It runs on the same engine as Fischer Random and Atomic Chess. The Dungeon Chess guide documents the full implementation: every hook, every adapter, every decision point for building a game ambitious enough to need its own renderer and AI configuration.

Moddable Hexmaps.

Hexmaps is a shared hexagonal map framework. It generates, renders, and edits hex-based game boards via Canvas. Flat-top or pointy-top, any ring count, seeded RNG for reproducible generation, click-to-edit, JSON export/import, and a full URL param API for embedding.

Six games already consume it:

  • Nukes uses it for territory maps with terrain generation across 2-6 rings
  • Talisman Worlds uses it for ring-based adventure boards with encounter pools
  • Twilight Imperium uses it for galaxy layouts from 3 to 8 players
  • Colony uses it for Seafarers-style terrain with number token constraints
  • Planet Mongo uses it for 127-hex planetary conquest maps
  • Endless Skies uses it for frontier exploration with wormhole and nebula tiles

The plugin architecture mirrors MCE. Each game registers through HexApp.registerGame with its own terrain palette, generation rules, and editor controls. The engine handles coordinate math, rendering, sidebar UI, and embed bridging. The game plugin handles flavour.

Moddable Rules.

The third pillar is still in development. Moddable Rules is a shared rulebook system that builds themed, paginated rulebooks from structured content. Every game and mod gets a versioned rulebook built from the same design tokens, fonts, and layout components.

It already ships rulebooks for Nukes, Hyper Imperium, Econopoly, Dungeon Chess, and Talisman Worlds, with Planet Mongo and Endless Skies in development. The build system generates OG images, search indices, and print-ready PDFs from the same source files.

When Moddable Rules stabilises, it becomes the content layer. The engines handle play. The rules handle publishing. One game definition, multiple outputs.

Why plugin architecture matters.

The four MCE guides demonstrate different reasons for needing extensible engines:

  1. Orda Chess needed custom pieces with divergent movement and attack patterns. The engine had to separate "how a piece moves" from "how a piece captures."
  2. Crazyhouse needed action moves, hand management, and non-standard move generation. The engine had to support moves that are not board-to-board.
  3. Poison Chess needed timed square effects and conditional legality. The engine had to model state that lives on tiles, not pieces.
  4. Dungeon Chess needed all of the above plus custom rendering, terrain, capture interception, and multi-step turns. The engine had to be a platform, not a library.

Each guide solved a different category of extensibility problem. Together they proved that one engine can host everything from a five-line rule tweak to a complete standalone game. The same principle drives Hexmaps: Nukes needs combat mechanics on hexes while Talisman needs encounter draws, but both share coordinate math, rendering, and generation.

Open-source everything.

Licensing model Engines are MIT-licensed. Game content (rules, art, brand) is proprietary or CC BY-SA. The infrastructure is open. The creative layer is protected. Anyone can fork an engine. No one can claim our games.

All three engines are MIT-licensed. The game content (rules, art, brand) is proprietary, but the infrastructure that runs it is open. Anyone can fork the chess engine to build their own variant. Anyone can use Hexmaps to prototype a hex game. Anyone can extend the rules system to publish their own rulebook.

This is deliberate. The engines improve faster when the community can contribute. Forks are free marketing. And our competitive advantage is not the code. It is the games, the community, and the ecosystem that ties them together.

How they work as one.

The engines are not just parallel projects. They feed into each other. Hexmaps generates the board diagrams that appear inside the Nukes and Planet Mongo rulebooks. MCE renders the position diagrams in the Dungeon Chess rulebook. Moddable Rules consumes static SVGs exported directly from both engines at build time. The online tools, the printed rulebooks, and the interactive players all draw from the same rendering code. One improvement to the hex renderer shows up simultaneously on hex.moddable.games, in the Nukes PDF, and embedded on this website.

That is the circular economy on display. MCE was built so Dungeon Chess could exist. Dungeon Chess pushed MCE to support terrain, custom rendering, and multi-step turns. Those capabilities then made it trivial to add 70 other variants. Hexmaps was built so Nukes could exist. Nukes pushed Hexmaps to support terrain generation, ring-based layouts, and embeddable exports. Those capabilities then made it trivial to add Planet Mongo, Talisman, TI4, and Colony. Rules was built so every game could ship a professional rulebook. The rulebooks pushed Rules to consume SVG output from both engines, closing the loop.

Each engine makes the next game cheaper. Each game makes the engine better. Everything is open-source, stable, and versioned. Build an engine right, build it once, and everything you ship on top of it compounds.
